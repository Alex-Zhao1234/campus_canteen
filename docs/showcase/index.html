项目介绍

到食堂之前，就知道今天哪个窗口别去。

面向大学生的食堂菜品级点评与推荐工具。评价对象精确到窗口和菜品，评价一次只要 5 秒，榜单按天更新。

打开产品 → GitHub 仓库 演示用，登录页输入任意 xxx@xxx.edu.cn 邮箱按回车就直接进去。免费托管，闲置后首次打开约需 1 分钟唤醒。接口文档见 /docs。
避雷优先一条踩雷的权重大于一条好评。先告诉你别去哪，再告诉你去哪。
5 秒评价好评 / 一般 / 踩雷三选一即可提交，不写长文，不传多图。
天级时效换厨师、涨价、今日特供，三天前的评价权重只剩一半。

为什么不用大众点评

食堂不是餐厅，决策方式完全不同

学生每天面临两到三次“食堂吃什么”的决策，决策时间以秒计，信息三天就过期。通用点评产品的粒度、频率和成本都不匹配这个场景。

维度通用点评产品本系统
评价对象店铺窗口 / 菜品
使用频率低频，偶尔聚餐每天 2–3 次
决策时间几分钟到几小时30 秒以内
信息时效月级天级，半衰期 3 天
核心价值发现避雷 > 发现
评价成本长文 + 多图5 秒一键评价

MVP 范围

只做四件事

MVP 的唯一目标是验证一个假设：学生愿意每天花 5 秒告诉别人“这顿饭怎么样”。评价行为跑不起来，推荐算法就没有数据基础。关注、私信、积分商城、外卖，这些都明确不做。

评分机制

踩雷更重，旧评价更轻

榜单不是简单的好评数减差评数。每条评价有一个基础分，再乘以随时间衰减的权重，最后做贝叶斯平滑，防止一条好评把新菜推到榜首。

+1.0好评 good
0.0一般 ok
−1.5踩雷 bad
# 单条评价的权重：半衰期 3 天，再乘用户可信度
weight(t) = 0.5 ^ (age_days / 3) × trust_score

# 菜品 7 日评分：贝叶斯平滑，k = 2
score_7d = Σ(base_i × weight_i) / (Σ weight_i + 2)
  • 踩雷的绝对值大于好评，体现“避雷优先”：一条踩雷比一条好评更值得被看到。
  • 平滑常数 k = 2 相当于预置了两条权重为 1 的中性评价。一条好评的新菜得分只有 0.33，上不了榜首。
  • trust_score 用于压低疑似刷评账号的影响，默认 1.0。

评价权重随天数衰减

trust_score = 1.0

7 天前的评价权重只剩约五分之一，14 天前的基本不再影响榜单。悬停查看任意一天的权重。

技术栈与架构

单机 SQLite 就够用的轻后端

目标是一所学校、一个食堂起步，日均百级评价量。选型以开发速度和部署简单为先，向量检索和 PostgreSQL 迁移留到后续阶段。

后端

  • Python 3.12 · FastAPI异步接口
  • SQLAlchemy 2.0 async · aiosqliteORM 与驱动
  • SQLite（WAL 模式）单文件数据库
  • Pydantic v2 · Alembic校验与迁移
  • APScheduler每 10 分钟重算榜单

前端

  • React 18 · TypeScript组件与类型
  • Vite构建与开发代理
  • TanStack Query服务端状态
  • Zustand本地状态
  • React Router页面路由
api→services→repositories→models   // 路由层不写业务逻辑；评价表 append-only，聚合指标全部派生
